# 0013. Сначала модель, потом схема; бренды для примитивов

Статус: предложено, 2026-10-22. Внедрение — `docs/domain-migration.md`, этапы 4–6.

## Контекст

Типы domain выводятся из zod (`z.infer`) через цепочки `extend`, `omit`, `partial`, `superRefine`.
Чтобы понять, что такое «месяц» или «категория», нужно мысленно выполнить zod. Контракт читается как
набор правил валидации, а не как описание предметной области.

Деньги, проценты, месяц, дата и id — везде `string`. Компилятор не мешает передать процент туда,
где ждут деньги, или id участника вместо id категории. Мусорная строка доходит до арифметики:
`toKopecks('abc')` возвращает `NaN`, и ничего не падает.

Инвариант категории (фиксированная сумма больше нуля, процент от 0 до 100) записан проверкой над
парой плоских полей `calculationMode` + `targetAmount`. `partial()` для обновления эту проверку
обходит: можно прислать только `targetAmount: '500'` у процентной категории или сменить режим без
суммы.

## Решение

### Модуль domain: модель, схема, правила, расчёт

- `<m>.model.ts` — только типы. Читается сверху вниз как словарь: JSDoc на языке предметной
  области, поля перечислены явно, без `extend` и пересечений. Сюда же — сценарии (что приходит на
  вход операции), названные по смыслу: `CreateCategory`, `SetPlannedIncome`, `CloseMonth`.
- `<m>.contract.ts` — zod-схемы, подчинённые модели: каждая схема заканчивается
  `satisfies z.ZodType<Тип>`. Схема, разошедшаяся с типом, не компилируется.
- `<m>.rules.ts` — условия допуска (ADR-0014), `<m>.calculation.ts` — расчёты, `<m>.enums.ts`,
  `<m>.errors.ts`, `index.ts` без `export *`.
- Дублирование полей между моделью и схемой допустимо: это цена читаемости.

### Бренды

- Примитив с правилами получает бренд: `Money` (неотрицательная decimal-строка), `SignedMoney`,
  `Percent` (0–100, две цифры после точки), `IsoDate`, `Period`, id сущностей (`MemberId`,
  `CategoryId`, `MonthlyBudgetId`, `ReceiptId`).
- Бренд — только тип, в рантайме это та же строка: через RSC, JSON и кэш `QueryClient` идёт как
  есть (ADR-0009 не меняется).
- Бренды вложенные: `Money` подходит туда, где ждут `SignedMoney`, `Period` — туда, где ждут
  `IsoDate`; обратно — нет.
- Бренд ставится только при разборе схемой (на входе экшена, в маппере `lib`, при чтении на
  клиенте) и внутри `domain/shared`. `as Money` в остальном коде запрещён.
- Функции `money.ts` и `date.ts` принимают и возвращают бренды и бросают исключение на значении,
  которое бренду не соответствует.

### Категория: требование одним полем

- Требование категории — объединение `CategoryTarget`: `{ mode: 'absolute'; amount }` или
  `{ mode: 'relative'; percent }`. Инвариант живёт внутри одного поля, и обновление меняет его
  только целиком; `partial()` над сценарием становится безопасным.
- БД остаётся плоской (`calculation_mode`, `target_amount`) и получает CHECK на инвариант; маппер
  `lib` переводит строку в объединение и обратно.

### Формы

Форма хранит значения в виде входа схемы (`z.input`), а на отправке получает результат разбора
(`z.output`) с брендами. Своих схем у формы по-прежнему нет.

## Альтернативы

- **Оставить `z.infer` как источник типа.** Ничего не стоит, но тип по-прежнему читается только
  через zod, а схема и есть модель.
- **`z.brand()` из zod.** Бренд выводится из схемы, то есть модель снова зависит от zod. Метка
  `z.$brand` видна в каждой подсказке и сообщении компилятора.
- **Value objects-классы (`new Money('10.00')`).** Экземпляры не переживают RSC и JSON в кэше:
  на клиент приходит простой объект без методов.
- **Effect Schema, Valibot, ArkType.** Читаемость даёт разделение «тип → схема», а не библиотека;
  смена библиотеки переписывает всё без выигрыша для модели.
- **Отдельный слой DTO и кодеков между проводом и моделью.** Потребитель контракта один, всё и так
  примитивы. Пересмотреть при втором потребителе.

## Последствия

- Модуль domain понимается по `model.ts` без чтения zod.
- Компилятор ловит перепутанные деньги и проценты, период и дату, id разных сущностей, режим
  категории без суммы.
- `satisfies` проверяет только в одну сторону: лишнее поле в схеме пройдёт, его выбросит разбор.
- Больше файлов в модуле и дублирование полей; при правке модели нужно поправить и схему (компилятор
  напомнит).
- Формы сложнее: два типа значений (`z.input` и `z.output`).
- На границе с БД нужен разбор схемой там, где раньше было простое присваивание.
- Правило CLAUDE.md «Выходная схема выводится из входной (`extend`)» заменяется этим ADR.

## Пересмотреть, если

- Появится второй потребитель контракта (мобильное приложение, публичный API) — тогда нужен
  отдельный слой контракта с версиями.
- zod или TypeScript получат проверку схемы по типу в обе стороны — тогда дублирование можно
  убрать генерацией.
- Трение брендов в формах и мапперах окажется дороже ошибок, которые они ловят.
