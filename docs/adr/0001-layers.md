# 0001. Слои и направление импортов

Статус: принято, 2026-09-30

## Контекст

В Next.js App Router один и тот же файл может выполняться и на сервере, и в браузере. Пока слоёв не
было, клиентский код оседал в серверном `lib`, server actions лежали внутри фич, а ключи кэша жили
в сторах фичи. У данных не было хозяина, и страница не могла загрузить их, не потянув за собой
фичу.

## Решение

Пять слоёв в `apps/web`: `app` (страницы и роуты), `features` (клиентские фичи), `components`
(общий UI), `client` (клиентская половина модулей: кэш, чтение, команды, синхронизация), `lib`
(серверные сценарии). Общий словарь сервера и клиента — пакет `domain`.

Импорты идут только сверху вниз, фичи друг друга не импортируют. Точная таблица разрешённых
импортов — в CLAUDE.md.

## Альтернативы

- Держать данные внутри фичи. Не подходит: кэш и SSE живут столько же, сколько вкладка, а не фича,
  и данные месяца понадобятся второй фиче (дашборд).
- Вынести клиентскую часть в отдельный пакет `packages/client`. Server actions собираются только
  внутри Next-приложения, а границу между слоями дешевле держать правилом линтера.

## Последствия

- У данных каждого модуля один хозяин на клиенте; страница загружает их, ничего не зная о фиче.
- По пути к файлу видно, где он выполняется и что ему можно импортировать.
- Путь от кнопки до БД длинный: виджет → VM → команда → экшен → сервис. Для простых форм это
  избыточно.
- Пока правило не закреплено в ESLint (`no-restricted-imports`), оно держится на дисциплине.
